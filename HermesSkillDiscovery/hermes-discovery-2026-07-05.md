## Chosen AI Problem Space

**Process Calculus, Petri Nets & Compositional Concurrency Verification for Deterministic Agent Workflows.**

### Rationale

Mainstream LLM agent frameworks (2024–2026 vintage) express multi-step behavior as prompt chains, ad-hoc DAG libraries, or "planner + executor" loops with no compositional semantics — no notion of interleaving, no reachability proof, no deadlock/livelock detection, no algebraic equivalence between two workflows that "do the same thing" via different paths. This is the widest epistemic gap between what Hermes needs (deterministic, replayable, long-horizon workflow execution with provable properties) and what the LLM-agent ecosystem actually ships.

Process calculus (CSP, CCS, π-calculus) and Petri nets are the pre-AI substrate that solved exactly this problem for distributed systems engineers from the 1960s–2000s: compositional concurrency, reachability analysis, place/transition invariants, and formal deadlock proofs. Adjacent substrates — temporal-logic model checking, relational model finding, Datalog/ASP solvers, durable-execution engines, plain-text double-entry ledgers, and rule-engine pattern matching (Rete) — were selected as satellite concepts because each encodes a *human-domain discipline* (bookkeeping, forensic scheduling, expert-system triage) that has a non-obvious structural isomorphism to a Hermes primitive (state reconciliation, task graph replay, hypothesis triage). This rotation deliberately excludes modern "agent framework" repos to surface pre-AI substrate the LLM tooling wave has not yet re-derived.

### 1. SNAKES — `fpom/snakes` (github.com/fpom/snakes)

**Concept observed:** Petri net algebra library where nets are built compositionally via explicit place/transition/arc objects, with a plugin system that layers new semantics (timing, stochastic weights, coloring) onto a common net kernel without modifying the kernel.

[HYPOTHESIS_MATRIX: 1. Hermes could represent every multi-step workflow internally as a SNAKES-style Petri net (places = state predicates, transitions = tool calls) to gain reachability analysis for free. 2. Hermes could adopt only the *plugin layering* pattern (compose orthogonal semantics without touching the core scheduler) to add retry/timeout/priority semantics to its DAG engine. 3. SNAKES' arbitrary-Python-object-as-token feature could let Hermes tokens carry live agent context (memory, tool-call results) through the net rather than opaque IDs.]

[FALSIFICATION_CRITERIA: H1: falsified if Hermes' task graphs commonly contain non-monotonic state (state that can be un-set, not just added), which classical P/T nets cannot represent without unbounded place proliferation. H2: falsified if the plugin system requires modifying the net *kernel* (not just adding a plugin) to add a new cross-cutting concern, indicating the isolation claim doesn't hold under real extension pressure. H3: falsified if token payloads must be serialized for persistence (durable execution), defeating the "arbitrary Python object" advantage.]

[EPISTEMIC_DELTA: H1 — Hermes workflows routinely retract state (e.g., "hypothesis invalidated," "file lock released") which full P/T nets model only via inhibitor arcs or colored tokens, both of which SNAKES supports but at a modeling-complexity cost that erodes the "free reachability" benefit. Steelman for confirm: SNAKES' colored/inhibitor extensions handle this natively. Steelman for falsify: adopting inhibitor arcs pushes net design into full Turing-completeness territory, forfeiting the decidability that motivated using nets at all. **FALSIFIED** — the net gains expressivity by giving up the analyzability that was the entire point. H2 — inspected `snakes/plugins/__init__.py`-style dynamic mixin loading: plugins subclass and monkey-patch net/place/transition classes at import time, meaning a plugin CAN override kernel dispatch, but well-behaved plugins (draw, time, gal) demonstrably don't need to. Ontology gap: this maps a *library extension* mechanism onto what Hermes needs as a *runtime* extension mechanism (adding retry semantics to a workflow already mid-execution) — SNAKES plugins are load-time, not run-time. **CONFIRMED** with abstraction-gap flag: usable only for compile-time-composed workflow templates, not live-modification of in-flight workflows. Cost reference: near-zero marginal integration cost since it's a design pattern, not a dependency. H3 — durable execution (see Cadence, below) requires token payloads to survive process restarts. SNAKES tokens are unrestricted Python objects with no serialization contract. **FALSIFIED** for the durable-execution use case; still valid for ephemeral in-memory sub-workflows.]

### 2. TLA+ / TLC — `tlaplus/tlaplus` (github.com/tlaplus/tlaplus)

**Concept observed:** TLC exhaustively explores the reachable state space of a TLA+ specification and checks invariants/temporal properties, reporting a concrete counter-example trace on violation — not a proof, a *falsifying execution*.

[HYPOTHESIS_MATRIX: 1. Hermes could write a TLA+ spec of its own scheduler (task dependency resolution, retry/backoff, idempotency) and run TLC in CI to catch scheduler races before they hit production agents. 2. Hermes could adopt TLC's counter-example trace format as the canonical "why did this workflow fail" artifact, replacing ad-hoc stack traces with minimal reproducing state sequences. 3. Hermes could embed a lightweight state-space explorer as a *pre-execution* dry-run mode: before committing to a long-horizon plan, exhaustively explore small-bounded abstractions of the plan graph to detect deadlock/starvation.]

[FALSIFICATION_CRITERIA: H1: falsified if Hermes' actual scheduler state space is unbounded in a way that makes TLC's explicit-state exploration intractable even for small bounds (e.g., unbounded tool-call arguments as state variables). H2: falsified if Hermes' failure modes are dominated by *external* nondeterminism (flaky APIs, LLM sampling variance) rather than internal logic races, making a minimal internal counter-example uninformative. H3: falsified if the "small-bounded abstraction" of a real Hermes plan graph is not actually representative of the full-scale graph's failure modes (abstraction unsoundness).]

[EPISTEMIC_DELTA: H1 — Hermes state (task statuses, dependency edges) is finite and enumerable per-workflow-instance even though tool arguments are unbounded, because TLC only needs to model the *control* state, not data payloads (standard TLA+ practice: abstract data to a small enumerated domain). Steelman-falsify attempt: control state could still explode combinatorially with many parallel branches (state explosion). Counter: bounded model checking is explicitly a *finite-instance* tool, used per-topology not per-deployment. **CONFIRMED**, cost reference: authoring a TLA+ spec of a scheduler core is a 1–3 day investment per major scheduler version, comparable to writing an integration test suite, paid in Java/JVM (TLC requires JVM 11+) rather than the harness's native runtime — cross-runtime cost is real but bounded to CI, not production path. H2 — this is real: many Hermes failures are exogenous (rate limits, tool timeouts), which TLC-style internal model checking cannot surface by design (it verifies the model, not the world). **DEFERRED** — valid for the subset of failures that are logic races (double-execution, missed dependency), invalid as a general failure-detection strategy. Ontology gap named: TLA+ verifies a *model* of the system; Hermes needs verification of the *system's interaction with an adversarial external world*, which is a strictly larger problem TLA+ does not claim to solve. H3 — abstraction soundness must be argued per-spec; no general guarantee. **DEFERRED**, contingent on discipline in spec-writing (standard TLA+ practice: refinement mapping from abstract to concrete spec) which Hermes does not yet have tooling to enforce automatically.]

### 3. hledger — `simonmichael/hledger` (github.com/simonmichael/hledger)

**Concept observed:** A plain-text, append-only, human-readable ledger format where every transaction is a balanced double-entry (debits = credits), auditable by diffing the text file directly, with no schema migration ever required because entries are immutable once written.

[HYPOTHESIS_MATRIX: 1. Hermes could log every agent action as a "double-entry" pair — a debit from "intended state" and a credit to "achieved state" — making workflow audit trails self-balancing and diffable exactly like financial ledgers. 2. Hermes could adopt hledger's append-only plain-text-file-as-source-of-truth pattern for its own task/session history, replacing a database with a git-diffable format for provenance and reproducibility. 3. Hledger's "balance assertion" syntax (asserting an account's running balance at a checkpoint) could become Hermes' mechanism for asserting workflow invariants at checkpoints without a full model checker.]

[FALSIFICATION_CRITERIA: H1: falsified if agent actions are not naturally decomposable into a balanced-pair structure (i.e., "intended" and "achieved" are not conserved quantities the way money is). H2: falsified if Hermes' task history volume or query patterns (e.g., needing indexed lookups across millions of steps) make flat-file text scanning infeasible without reintroducing a database anyway. H3: falsified if balance assertions require a total order over checkpoints that concurrent/parallel Hermes sub-workflows cannot provide.]

[EPISTEMIC_DELTA: H1 — money is a conserved quantity (double-entry works because debits structurally must equal credits); agent intent/achievement is not conserved in this sense — an agent can intend five things and achieve zero, with no balancing entry required. Ontology gap named explicitly: this hypothesis maps a *conservation-law domain* (accounting) onto a *non-conservation domain* (agent action outcomes), and the isomorphism is metaphorical, not structural. **FALSIFIED**. H2 — hledger itself scales to years of personal finance data (thousands of transactions) via plain text but explicitly recommends splitting files/using included journals for larger corpora; Hermes production logs (potentially millions of tool calls/day) exceed this regime by orders of magnitude. **FALSIFIED** for production-scale logging; **CONFIRMED** narrowly for local/dev-mode session journals where human-diffability during debugging is the priority over query performance. Cost reference: adopting plain-text journal format costs nothing extra at dev scale (Hermes likely already writes JSON logs; switching serialization is a day of work) but would require re-introducing indexing infrastructure at production scale, negating the benefit. H3 — balance assertions in hledger are declared at file-write time by a single author process, implicitly sequential. Hermes sub-workflows run concurrently, and "checkpoint order" is not globally well-defined without a synchronization protocol Hermes doesn't yet have. **DEFERRED**, dependent on whether Hermes adopts a vector-clock or Lamport-timestamp ordering scheme (see CRDT/causal-history literature, not covered in today's batch — flagged for a future run).]

[FALSIFICATION_CRITERIA: H1: falsified if any existing Hermes report/dashboard already requires mutable side-state (e.g., manually-annotated triage flags) that cannot be re-derived from raw history alone. H2: falsified if Hermes task history lacks a natural hierarchical "account" structure analogous to ledger's chart of accounts. H3: falsified if the "common budget unit" conversion requires exchange rates that are themselves agent-generated (circular dependency — the conversion needs the thing it's trying to price).]

[EPISTEMIC_DELTA: H1 — this is a well-known and good architectural discipline (cf. "derived state" / event sourcing) independently of ledger; ledger is a strong existence-proof that a mature, decades-old CLI tool enforces this successfully at scale. H2 — Hermes task graphs do have natural hierarchy (workflow → sub-workflow → task → tool-call), directly analogous to ledger's account:subaccount:subsubaccount colon-path convention. **CONFIRMED** — a colon-delimited task-path convention plus a ledger-style query grammar is a near-direct port. Cost reference: implementing a small query grammar parser is comparable effort to ledger's own query engine (a few hundred lines), a multi-day task, far cheaper than standing up a full analytics DB for the same query surface. H3 — real risk: if "cost" includes agent-estimated risk/confidence scores, and those scores are produced by the same models being audited, the exchange rate is self-referential in a way currency exchange rates (set by external markets) are not. **FALSIFIED** for the risk/confidence dimension specifically; **CONFIRMED** for the objectively-measurable dimensions (tokens, dollars, wall-clock latency), which have no circularity.]

### 5. Alloy Analyzer — `AlloyTools/org.alloytools.alloy` (github.com/AlloyTools/org.alloytools.alloy)

**Concept observed:** A relational-logic modeling language backed by a SAT solver (Kodkod) that, given a small bound on universe size, either finds a concrete instance satisfying a spec or proves none exists within that bound — used for finding design flaws by generating counterexamples, not for proving correctness at scale.

[HYPOTHESIS_MATRIX: 1. Hermes could model its permission/capability system (which tools an agent can invoke under what preconditions) in Alloy to automatically discover privilege-escalation paths (a sequence of legal tool calls that reaches an illegal state) before deployment. 2. Alloy's "bounded scope" philosophy (deliberately checking small instances exhaustively rather than large instances heuristically) could inform a Hermes testing strategy: generate all small workflow topologies up to N tasks and verify a property holds for all of them, as a complement to unit tests. 3. Alloy's visualizer (rendering found instances as relational graphs) could be repurposed as a Hermes workflow-graph debugging visualizer, since both are fundamentally rendering relations/tuples as node-edge diagrams.]

[FALSIFICATION_CRITERIA: H1: falsified if Hermes' permission model includes continuous/numeric preconditions (budgets, rate limits) that don't reduce to the finite relational atoms Alloy reasons over without lossy discretization. H2: falsified if bugs in real Hermes workflows are dominated by large-N emergent behavior (e.g., race conditions requiring many concurrent tasks) that small-bounded exhaustive search by construction cannot reach. H3: falsified if Alloy's visualizer is tightly coupled to its own relational-tuple internal representation in a way that can't ingest an arbitrary external graph without re-deriving the whole Alloy relational model first.]

[EPISTEMIC_DELTA: H1 — genuine numeric preconditions (budgets, rate limits) do need discretization (e.g., "budget: {low, medium, high}") which is a real modeling cost but is standard Alloy practice. This is a cost, not a structural blocker. **CONFIRMED** with named cost: discretization introduces a soundness gap (a discretized-safe model may hide a real continuous-domain vulnerability at boundary values) that must be documented per-model. Cost reference: comparable engineering investment to writing property-based tests — a few days per subsystem, with the advantage of exhaustiveness within the bound versus property tests' random sampling. H2 — this is a known, well-documented limitation of bounded model finding generally (the "small scope hypothesis" is Alloy's own explicit, named assumption) — most bugs manifest at small scope, but concurrency races are the canonical counterexample class that needs larger N. **DEFERRED** — valid for permission/state-machine-shaped bugs, explicitly not claimed by Alloy's own authors to catch concurrency-scale races (that's SPIN/TLA+ territory). H3 — inspected: Alloy's visualizer consumes Alloy's own instance format exclusively; there is no adapter for arbitrary external relational data without first encoding it as an Alloy instance. **FALSIFIED** as a general-purpose Hermes graph visualizer; narrowly **CONFIRMED** only if Hermes workflows are already modeled in Alloy for H1, in which case the visualizer comes "for free" as a byproduct, not as an independently portable component.]

### 6. Soufflé — `souffle-lang/souffle` (github.com/souffle-lang/souffle)

**Concept observed:** A Datalog dialect that compiles logic-program specifications into native parallel C++ for large-scale static analysis, distinguishing itself by treating "the analysis" as declarative fixpoint rules over relations rather than an imperative traversal algorithm.

[HYPOTHESIS_MATRIX: 1. [FALSIFICATION_CRITERIA: H1: falsified if Hermes scheduling requires negation-as-failure over unbounded/streaming fact additions, which stratified Datalog handles awkwardly compared to incremental/streaming variants. H2: falsified if Hermes' permission graph already has a purpose-built graph library that performs equivalently without introducing a second language into the stack. H3: falsified if the "compile declarative rules to native code" step's compile-time latency is incompatible with Hermes' need for workflows to be defined and executed within the same short session.]

[EPISTEMIC_DELTA: H1 — Datalog is exactly the right tool for monotonic reachability/readiness computation, but Hermes scheduling does involve non-monotonic facts (a task's dependency being *invalidated* after being satisfied, e.g., stale cache). H3 — verified from Soufflé docs/benchmarks: synthesis (compilation) is a build-time step separate from execution; for large static-analysis programs it can take real wall-clock minutes, fine for CI-time analysis but wrong for interactive/dynamic workflow definition within a single agent session. **FALSIFIED** for the "define and run in the same session" use case named in the hypothesis; narrower **CONFIRMED** if restricted to interpreted mode for dynamic session use and compiled mode reserved for stable, reused workflow templates.]

### 7. clingo — `potassco/clingo` (github.com/potassco/clingo)

[EPISTEMIC_DELTA: H1 — ASP grounding blowup is a real, well-documented practical limitation; for Hermes-scale plans (tens to low hundreds of candidate branches) it is very likely tractable, but this is an empirical claim requiring benchmarking against actual Hermes plan-graph sizes. **DEFERRED**, pending an actual benchmark against a representative Hermes plan graph — flagged as the highest-value follow-up experiment from this run. ### 8. Fast Downward — `aibasel/downward` (github.com/aibasel/downward)

H3 — untested against real Hermes data; empirical claim requiring benchmarking, not resolvable from documentation alone. **DEFERRED**, flagged as follow-up experiment.]

### 9. Cadence — `cadence-workflow/cadence` (github.com/cadence-workflow/cadence)

**Concept observed:** A durable-execution orchestration engine where workflow code is written as ordinary sequential code, but the *engine* persists every state transition as an event history, allowing the workflow to be transparently replayed from any point after a crash/restart — the programmer never writes explicit checkpoint/resume logic.

[HYPOTHESIS_MATRIX: 1. Hermes could adopt Cadence's event-sourcing/replay model directly as its execution substrate for long-horizon tasks. 2. Cadence's strict requirement that workflow code be *deterministic* (nondeterminism quarantined into "activities") is a discipline Hermes should impose on its own planning layer, quarantining all LLM-sampling nondeterminism into clearly-marked activity boundaries. 3. Cadence's built-in retry/backoff/timeout policies per-activity could be lifted wholesale as Hermes' per-tool-call reliability policy layer.]

[FALSIFICATION_CRITERIA: H1: falsified if Hermes' per-step state (full LLM context windows, large intermediate artifacts) is too large/expensive to persist as replayable event history at the granularity Cadence expects. H2: falsified if LLM calls cannot be cleanly quarantined as "activities" because planning and control flow are *interleaved* with LLM sampling at every step. H3: falsified if Hermes needs retry semantics that are content-aware (e.g., "retry with a modified prompt"), which generic activity-retry policies do not support without custom logic anyway.]

[EPISTEMIC_DELTA: H1 — real cost concern: Cadence event histories are optimized for compact business-logic events, not multi-kilobyte-to-megabyte LLM context blobs; naively persisting full context would bloat history size and replay time. Mitigation exists (activities can return references to externally-stored large payloads — a documented "claim check" pattern) but requires deliberate design. **CONFIRMED** with a required architectural adaptation (externalize large payloads, persist only references). Cost reference: comparable to adding a blob-storage layer alongside any event-sourced system — days not weeks. H2 — this is the crux ontology gap: Hermes' "workflow logic" is frequently itself produced by an LLM call, meaning the boundary between deterministic orchestration and nondeterministic activity is blurrier than in Cadence's original business-workflow use case. Named abstraction gap: Cadence assumes a human author writes the deterministic skeleton; Hermes' skeleton is itself sometimes agent-authored and therefore itself nondeterministic, requiring the *skeleton-generation* step to be its own quarantined activity whose *output* becomes the replayable deterministic plan. **CONFIRMED, with the ontology gap explicitly named and a required architectural adaptation** (two-phase: plan-generation as an activity producing a fixed plan artifact, then execution of that fixed plan as the deterministic workflow proper). H3 — legitimate limitation acknowledged: Cadence retry policies are content-blind by design; content-aware retry must be implemented as explicit workflow logic wrapping the activity call. **DEFERRED** — the generic policy layer is still valuable for the content-blind subset of failures (timeouts, rate limits, transient errors), a large and real fraction of tool-call failures, even though it doesn't cover the content-aware subset.]

### 10. CLIPS — `clipsrules/clipsrules` (github.com/clipsrules/clipsrules)
